# docker-compose.stress.yml Documentation

## Purpose
- Orchestrates a stress/load test stack: one server, one web dashboard, and many station clients (default 100) sending faster and larger batches to evaluate throughput and stability.
- Auto-generated by `scripts/gen_stress_compose.py` with configurable station count.

## High-level flow
- `server`: same build/env/volume/healthcheck as normal compose.
- `web`: same as normal compose, sharing the DB volume read-only.
- `station-stress-001 .. station-stress-N`: each built from `station_client/Dockerfile`, depend on server health, send every 1s with batch size 1–5, unique IDs `STRESS-###`.
- Shared `weather-network` bridge; shared named volume `weather-data` for SQLite.

## Key data structures
- Volume: `weather-data` shared read/write (server) and read-only (web) across all clients.
- Network: `weather-network` bridge.
- Environment per stress client: host `server`, port 12345, ID `STRESS-###`, batch min 1, max 5, interval 1s, timeout 5s, retries 3.

## Error handling & edge cases
- Healthcheck gates client startup; if server fails, clients will stay pending.
- Heavy client count can push SQLite or CPU; if `database is locked` appears, consider reducing station count or increasing resources.
- Host port conflicts on 12345/8000 similar to normal compose.

## Performance & scalability notes
- High write rate: relies on server single-writer queue and SQLite WAL to avoid lock contention, but DB remains a bottleneck under extreme load.
- Web UI may lag when charting many points; consider narrowing time windows or sampling.

## How to test this file
- Run: `docker compose -f docker-compose.stress.yml up --build`.
- Monitor: `docker stats` for resource usage; `docker compose logs server` for inserts/errors; UI at http://localhost:8000 to confirm data flow.
- Clean up: `docker compose -f docker-compose.stress.yml down -v` to remove containers and the volume.
