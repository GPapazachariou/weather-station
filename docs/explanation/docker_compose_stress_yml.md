# docker-compose.stress.yml — Explanation

**Related docs:** [00_overview.md](00_overview.md), [docker_compose_yml.md](docker_compose_yml.md), [dockerfile_server.md](dockerfile_server.md), [dockerfile_station_client.md](dockerfile_station_client.md)

## Purpose

The stress test Docker Compose file is auto-generated by [scripts/gen_stress_compose.py](../scripts/gen_stress_compose.py) and configures 100 weather station clients to simultaneously send data at high frequency (1-second intervals, 1-5 readings/batch). This tests server resilience, database concurrency, network throughput, and dashboard performance under load. Use this for load testing and capacity planning.

## Key Responsibilities

- Define 1 TCP server, 1 web UI (same as normal mode)
- Generate 100 station client services (STRESS-001 to STRESS-100)
- Configure aggressive parameters: 1-second batch interval, 1-5 readings per batch
- Maintain same volume and network configuration as normal mode
- Allow customization via `scripts/gen_stress_compose.py --stations <count>`
- Support easy cleanup via `docker compose -f docker-compose.stress.yml down -v`

## Important Blocks

### Block: Auto-Generated Header Comment

**Where:** Top 20 lines

**What it does:**
Explains that the file is auto-generated, lists parameters, and shows usage examples:

```yaml
# ============================================================================
# STRESS TEST DOCKER COMPOSE FOR WEATHER STATION SIMULATOR
# ============================================================================
# This compose file is auto-generated by scripts/gen_stress_compose.py
# It runs:
#   - 1 TCP server (port 12345)
#   - 1 web dashboard (port 8000)
#   - 100 weather station clients with stress parameters:
#       - Fast interval: 1 second between batches
#       - Larger batches: 1-5 readings per batch
#       - Unique IDs: STRESS-001 to STRESS-100
#
# USAGE:
#   Generate (with custom count):
#     python scripts/gen_stress_compose.py --stations 100
#
#   Run:
#     docker compose -f docker-compose.stress.yml up --build
#
#   Clean up:
#     docker compose -f docker-compose.stress.yml down -v
# ============================================================================
```

**Inputs:** Python script gen_stress_compose.py

**Outputs:** Human-readable instructions for users

**Why it matters:** Users understand this is auto-generated and how to regenerate/run it

### Block: Server Service (Identical to Normal Mode)

**Where:** `services.server { ... }`

**What it does:**
Same configuration as `docker-compose.yml`:
- TCP server on port 12345
- Mounts weather-data volume
- Environment variables (SERVER_HOST=0.0.0.0, SERVER_PORT=12345, DB_PATH=/app/data/weather.db)
- Health check on TCP port
- Restart policy: unless-stopped

**Inputs:** Dockerfile, network, volume

**Outputs:** Running TCP server

**Why it matters:** Must be identical so server doesn't become the bottleneck; single writer task handles 100 concurrent clients

**Failure modes:** See [docker_compose_yml.md](docker_compose_yml.md#failure-modes-1)

### Block: Web Service (Identical to Normal Mode)

**Where:** `services.web { ... }`

**What it does:**
Same configuration as `docker-compose.yml`:
- Flask on port 8000
- Read-only mount of weather-data volume
- Environment variables (WEATHER_DB_PATH, WEB_HOST=0.0.0.0, WEB_PORT=8000)
- Depends on: server (ordering)

**Inputs:** Dockerfile, network, volume

**Outputs:** Running Flask dashboard

**Why it matters:** Visualize stress test in real-time; monitor database growth

### Block: 100 Station Client Services

**Where:** `services.station-stress-001 { ... }` through `services.station-stress-100 { ... }`

**What it does:**
Each of 100 identical services (pattern repeats):
1. Builds from `./station_client/Dockerfile`
2. Container name: `weather-stress-station-001` through `weather-stress-station-100`
3. Environment variables:
   - `WEATHER_STATION_HOST=server`
   - `WEATHER_STATION_PORT=12345`
   - `WEATHER_STATION_ID=STRESS-001` through `STRESS-100` (unique per service)
   - `WEATHER_STATION_BATCH_MIN=1` (minimum 1 reading per batch)
   - `WEATHER_STATION_BATCH_MAX=5` (maximum 5 readings per batch; randomized)
   - `WEATHER_STATION_BATCH_INTERVAL=1` (send every 1 second, vs. 5 in normal mode)
   - `WEATHER_STATION_TIMEOUT=5.0`
   - `WEATHER_STATION_MAX_RETRIES=3`
4. Restart: unless-stopped
5. Depends on: server: condition: service_healthy
6. Network: weather-network

```yaml
station-stress-001:
  build:
    context: ./station_client
    dockerfile: Dockerfile
  container_name: weather-stress-station-001
  environment:
    - WEATHER_STATION_HOST=server
    - WEATHER_STATION_PORT=12345
    - WEATHER_STATION_ID=STRESS-001
    - WEATHER_STATION_BATCH_MIN=1
    - WEATHER_STATION_BATCH_MAX=5
    - WEATHER_STATION_BATCH_INTERVAL=1
    - WEATHER_STATION_TIMEOUT=5.0
    - WEATHER_STATION_MAX_RETRIES=3
  depends_on:
    server:
      condition: service_healthy
  restart: unless-stopped
  networks:
    - weather-network

# ... (pattern repeats for station-stress-002 through station-stress-100)
```

**Inputs:** Dockerfile, network

**Outputs:** 100 concurrent clients sending data

**Why it matters:**
- **100 concurrent clients** tests server's ability to handle multiple connections simultaneously
- **BATCH_INTERVAL=1** instead of 5 increases message frequency 5x (normal: 1 msg/5s → stress: 1 msg/1s)
- **BATCH_MAX=5** instead of 1 varies batch size (randomized 1-5 vs. fixed 1)
- **STRESS- prefix** in IDs (vs. STATION-) helps identify stress test data in logs
- Collectively: 100 clients × 1 msg/sec × avg 3 readings/msg = **~300 readings/sec** vs. 0.6 readings/sec in normal mode
- Tests single-writer task concurrency, TCP multiplexing, SQLite write throughput

**Failure modes:**
- Server crashes under load → clients loop with exponential backoff
- TCP listen backlog full → client connection refused → backoff + retry
- SQLite "database is locked" → writer task queue overflows or stalls
- Host CPU saturated → containers lag, timeouts increase

### Block: Volumes & Networks (Identical to Normal Mode)

**Where:** `volumes.weather-data { ... }` and `networks.weather-network { ... }`

**What it does:**
Same as `docker-compose.yml`:
- Named volume weather-data with local driver
- Bridge network weather-network

**Inputs:** Docker daemon

**Outputs:** Persistent storage and inter-service networking

**Why it matters:** Stress test uses same infrastructure; only client count/frequency differs

## Data & State

### Stress Parameters (vs. Normal Mode)

| Parameter | Normal Mode | Stress Mode | Reason |
|-----------|-------------|------------|--------|
| Station Clients | 3 | 100 | Test scalability |
| Batch Interval | 5 sec | 1 sec | 5x more frequent |
| Batch Min | 1 | 1 | Same |
| Batch Max | 1 | 5 | Variable batch sizes |
| Estimated Throughput | 0.6 readings/sec | 300 readings/sec | 500x increase |
| Unique Station IDs | STATION-001/002/003 | STRESS-001 to STRESS-100 | Easy identification |

### Expected Data Volume

```
Stress test duration: 1 hour

Readings per client per second: 1 batch = 1-5 readings (avg 3)
Total readings per second: 100 clients × 3 readings = 300 readings/sec
Total readings per hour: 300 × 3600 = 1,080,000 readings
Approximate database size: ~100-150 MB (SQLite stores readings + indices)

Memory usage:
  - Server: ~50 MB (asyncio, single writer task, network buffers)
  - Each client: ~10-15 MB (Python runtime, connection, buffer)
  - Total: ~50 + (100 × 12) = ~1250 MB
  - Web UI: ~20-30 MB
  - Total system: ~1.3 GB
```

### Client ID Pattern

- **Normal mode:** `STATION-001`, `STATION-002`, `STATION-003`
- **Stress mode:** `STRESS-001`, `STRESS-002`, ..., `STRESS-100`
- IDs are queryable; can filter stress data separately in dashboard

## Control Flow Walkthrough

### Generation & Setup

```
1. $ python scripts/gen_stress_compose.py --stations 100

2. Script gen_stress_compose.py:
   - Creates docker-compose.stress.yml file
   - Writes header comment with parameters
   - Writes server service definition
   - Writes web service definition
   - Loop 100 times:
       - Generate station-stress-001 to station-stress-100 service definition
       - Each has unique WEATHER_STATION_ID
   - Writes volumes and networks sections
   - Closes file

3. docker-compose.stress.yml now ready (~2000 lines)
```

### Startup

```
$ docker compose -f docker-compose.stress.yml up --build

1. Docker Compose reads docker-compose.stress.yml

2. Builds images (same as normal mode):
   - server/Dockerfile
   - station_client/Dockerfile (reused for all 100 services)
   - web/Dockerfile

3. Creates volume weather-data, network weather-network

4. Starts server:
   - TCP server listening on 12345
   - Health check begins after start_period: 10s
   - Within 5-10s, becomes "healthy"

5. Once server healthy, starts all 100 station clients:
   - Docker Compose starts them concurrently (or in parallel batches)
   - Each connects to server:12345
   - Each enters batch send loop (1-second interval)

6. ~5-10s: All 100 clients sending:
   - Total ~300 readings/sec flowing into server
   - Server multiplexes connections, single writer task queues batches
   - SQLite writes at high throughput

7. Web UI also started:
   - Queries database on each /api/stats or /api/readings request
   - Read-only access doesn't compete with writer
   - Visualizes growing data in real-time

8. Monitor with:
   - $ docker compose -f docker-compose.stress.yml ps (all 102 containers)
   - $ docker compose -f docker-compose.stress.yml logs -f server (batch arrivals)
   - $ open http://localhost:8000 (dashboard)
```

### Data Accumulation During Test

```
Minute 1: 300 readings/sec × 60 sec = 18,000 readings
         Database size: ~2 MB

Minute 10: 180,000 readings total
          Database size: ~15 MB

Hour 1: 1,080,000 readings total
       Database size: ~100 MB
       Dashboard query performance degrades if no indices
       (But schema has indices on timestamp, station_id)
```

### Stress Test Cleanup

```
$ docker compose -f docker-compose.stress.yml down -v

1. Stops all 102 containers (server, web, 100 clients)
2. Removes containers, network
3. Deletes volume weather-data (all readings lost)

Alternative (keep data):
$ docker compose -f docker-compose.stress.yml down

1. Stops containers
2. Removes containers, network
3. Keeps volume (data persists)
```

## Observability & Debugging

```bash

watch 'docker compose -f docker-compose.stress.yml ps | grep stress'

```

### Performance Benchmarking

```bash
# Measure readings inserted per second (after stabilization)
sqlite3 /app/data/weather.db "SELECT COUNT(*) FROM readings;" > start.txt
sleep 10
sqlite3 /app/data/weather.db "SELECT COUNT(*) FROM readings;" > end.txt
# Calculate: (end - start) / 10 = readings/sec
```

### Common Stress Test Issues

| Issue | Cause | Solution |
|-------|-------|----------|
| "Too many open files" | OS file descriptor limit | `ulimit -n 4096` or increase system limit |
| Server response lag | CPU bottleneck | Reduce client count or batch frequency |
| "database is locked" frequently | SQLite writer task overwhelmed | Check server logs; may indicate protocol issue |
| Dashboard slow | Too many records for charting | Use filters; reduce time window in UI |
| Client connections timeout | Network saturation or server backlog | Monitor TCP connections with `netstat` |
| Memory grows unbounded | Memory leak in server or client | Check logs for repeated allocations |

### Logging & Troubleshooting

```bash
# Capture server logs during stress test
docker compose -f docker-compose.stress.yml logs --timestamps server > stress_test.log

# Inspect single client logs
docker compose -f docker-compose.stress.yml logs stress-station-001

# Check if any clients failed to connect
docker compose -f docker-compose.stress.yml logs | grep -i "connection"

# Count successful batches in server log
docker compose -f docker-compose.stress.yml logs server | grep -c "Batch"
```

### Database Inspection After Stress Test

```bash
# Connect to database inside running server
docker compose -f docker-compose.stress.yml exec server sqlite3 /app/data/weather.db

# Inside sqlite3:
sqlite> SELECT station_id, COUNT(*) AS count FROM readings GROUP BY station_id LIMIT 10;
# Shows distribution of readings across clients

sqlite> SELECT COUNT(*) FROM readings WHERE station_id LIKE 'STRESS-%';
# Count total stress test readings

sqlite> SELECT MIN(timestamp), MAX(timestamp) FROM readings;
# Show time range of data collected

sqlite> PRAGMA table_info(readings);
# Verify schema

sqlite> .quit
```
